## 統合サンプルを読む(`weave_spec.md` §16)

ここまでの章で見てきた要素——アクター(5章)・カリー化(2章)・プロトタイプOOP(3章)・Go資産連携(6章)・モジュール(7章)——を1つのプログラムに組み合わせてみましょう。「文字列の長さを測るアクター」が、Go標準ライブラリの`strings.Reader`をWeaveオブジェクトと同じ書き味で扱います。

```weave
// --- Go資産の宣言(冒頭でまとめて行う。6章) ---
GoReader = gotype("?*strings.Reader", {
	len: gomethod("Len")
})
newReader = gofunc("?strings.NewReader", GoReader)

// --- Weave自身のプロトタイプ(3章) ---
readerProto = {
	measure: fn(self, replyTo) {
		result = newReader(self.text)   // Go資産の呼び出し(6章)
		r = at(result, 0)                // 戻り値は常にlist
		lenResult = r.len()               // r自身はGo由来だが、.method()という
		reply(replyTo, at(lenResult, 0))   // 同じ書き味で呼べる(0章の統一原理)
	}
}

main = fn(args) {
	// アクター(5章)に、自身のプロトタイプ+テキストを持つオブジェクトをスポーンする
	a = spawn({ __proto__: readerProto, text: "hello, weave" })
	n = ask(a)("measure")   // メッセージ送信=プロパティ検索の遠隔呼び出し(5章)
	print(n)                  // 12

	return n
}
```

`a`(アクター)の内部状態に保持された`self.text`は普通のWeave文字列で、`self.measure`のハンドラの中で`gofunc`/`gomethod`宣言済みのGo資産(`newReader`・`r.len()`)を呼び出しています。`r`(`strings.Reader`)はWeave自身のプロトタイプオブジェクトではなくGo資産由来の値ですが、`.len()`という**全く同じ構文**でメソッドを呼べていることに注目してください——0章で最初に紹介した「1つの仕組みへの統一」が、アクター・カリー化・プロトタイプOOP・Go資産連携という4つの要素を組み合わせた、この短い例の中に全て収まっています。

## 「できないこと」を知る(`weave_spec.md` §18)

Weaveには、意図的に持たせていない機能がいくつもあります。仕様書18章「現状の仕様でできないこと」は、「まだ実装されていないだけで、いずれ対応する予定」というリストではなく、**現時点のWeaveの設計上、構文として書けない・意味論として存在しないもの**を明示的に列挙したものです。たとえば:

- カウンタ・範囲形の`for`(`for i = 0; i < 10; i++`のような)は無い(4章で見た`for k, v in list(...)`が最も近い代替です)
- オブジェクト同士・関数同士を`==`で比較すると、実行時にクラッシュする
- 例外処理(`try`/`catch`)は無い——エラーは実行時パニックとしてしか起こらない(5章のアクターハンドラ内エラーもこの一種です)。ただし`recover(...)`という、Goの`defer`+`recover()`に直接対応する狭い回復手段はある(8章)——アクターのメッセージハンドラの中では使えない、という制約付き
- 相互再帰(2つの関数が互いを呼び合う)は無く、直接の自己再帰のみ対応している

このリストを一度読んでおくと、「これは書けるはずなのに、なぜエラーになるのだろう」と仕様書を読み返す時間を減らせます。
